# АС Поставщиков — RSocket

Учебное клиент-серверное приложение на Java 17, Spring Boot 3.5.7 и Project Reactor. Передача JSON по RSocket/TCP, порт 7000. Сервер и консольный клиент запускаются отдельными процессами из одного JAR.

## Предметная область

Используется модель frontend `../Bootcamp/bootcamp-ui-kit-dunya-iTt7f`: товары `Good(id, name, price)`, склады `Darkstore(id, address)`, доставки `Delivery(id, deliveryDatetime, darkstore, status)` и позиции доставки `GoodsList(good, count)`. Цены представлены `BigDecimal`. Два склада, две доставки и десять товаров хранятся в памяти; после перезапуска состояние сбрасывается.

Сущности и связи сверены с исходниками модуля «Front-end АС Поставщиков» BootcampLabs:

| Исходный компонент | Соответствие RSocket |
|---|---|
| `Good.tsx`: `GoodSource`, HTTP `/good` | `Good` с полями `id`, `name`, `price`; карточка и поток товаров |
| `Delivery.tsx`: чтение HTTP `/delivery` | `Delivery` с вложенным `darkstore`; статусы `SUBMITTED`, `ASSEMBLY`, `DELIVERY`, `COMPLETED`, `CANCELLED` |
| `Delivery.tsx`: чтение HTTP `/darkstore` | `Darkstore(id, address)`; адрес склада доставки |
| `GoodsList.tsx`: HTTP `/goodslist/delivery/{id}` | Поток `GoodsList` с вложенным `good` и количеством `count` |
| `Delivery.tsx`: выбор статуса и `saveNewDelivery("PUT")`, HTTP `PUT /delivery` | `deliveries.status`: изменение статуса доставки без ожидания ответа |
| `GoodsList.tsx`: «Изменить количество», `saveModifiedData("PUT", deliveryId, goodId, count)`, HTTP `PUT /goodslist` | `goodslist.channel`: поток изменений количества и результатов сохранения |

Товары взяты из предоставленного пользователем скриншота ответа `localhost:8080/good`, с сохранением ID, названий и цен. Адреса, даты и состав доставок остаются демонстрационными: для них конкретные записи не предоставлены. Отдельной сущности `Supplier` в данном frontend нет. Поле `deliveryDatetime` соответствует чтению ответа в `Delivery.tsx` (при записи frontend использует другое написание: `deliveryDateTime`). Сценарии интерфейса перенесены с HTTP на RSocket: изменение статуса передаётся как Fire-and-Forget, последовательные изменения количества — как Channel; транспортная модель отличается от frontend, само действие соответствует интерфейсу.

## Запуск

Нужны JDK 17+ и Maven 3.6.3+. Первый запуск сборки требует доступа к Maven Central.

```powershell
mvn clean package
```

Терминал 1 — сервер (профиль по умолчанию):

```powershell
java -jar target/suppliers-rsocket-1.1.0.jar
```

Терминал 2 — клиент:

```powershell
java -jar target/suppliers-rsocket-1.1.0.jar --spring.profiles.active=client
```

Для другого порта добавьте `--demo.port=7100` к обеим командам. Для подключения к другому компьютеру добавьте клиенту `--demo.host=адрес-сервера`.

При переходе со старой версии сначала остановите старый сервер через Ctrl+C, затем запустите сервер и клиент версии 1.1.0. Старый JAR 1.0.0 не содержит новых маршрутов и каталога. При проблемах с символами Windows выполните `chcp 65001` и запускайте Java с параметром `"-Dfile.encoding=UTF-8"` перед `-jar`.

Клиент выполняет все демонстрации по очереди и завершает работу. Сервер работает до Ctrl+C. При недоступном сервере клиент сообщает об ошибке и завершается с ненулевым кодом. Общий таймаут демонстрации — 30 секунд.

## Маршруты

| Модель | Маршрут | Вход | Выход |
|---|---|---|---|
| Request-Response | `goods.get` | ID товара, например `1` | `Mono<Good>` |
| Request-Response | `darkstores.get` | ID склада | `Mono<Darkstore>` |
| Request-Response | `deliveries.get` | ID доставки | `Mono<Delivery>` с вложенным складом |
| Request-Stream | `goods.stream` | `{"deliveryId":null}` — каталог; `{"deliveryId":2}` — товары доставки №2 | `Flux<Good>`, по одному каждые 400 мс |
| Request-Stream | `deliveries.goods` | ID доставки | `Flux<GoodsList>`: товар и количество каждые 400 мс |
| Fire-and-Forget | `deliveries.status` | `{"deliveryId":1,"status":"ASSEMBLY"}` | Нет ответа; статус сохраняется |
| Channel | `goodslist.channel` | Поток `{"deliveryId":1,"goodId":1,"count":4}` | Поток `GoodsListResult`: результат изменения количества |

`CatalogController` задаёт маршруты, `CatalogService` содержит каталог и логику, `DemoClient` — реактивный сценарий клиента, `Models` — DTO.

## Что видно при демонстрации

1. Request-Response: карточка пиццы «Маргарита», адрес склада и доставка с вложенным складом.
2. Запрос товара 999: ошибка «Товар 999 не найден». Клиент обрабатывает её через `onErrorResume` и продолжает сценарий.
3. Request-Stream: один запрос возвращает десять отдельных объектов. Время печатается для каждого элемента; между ними примерно 400 мс. После строки получения клиент применяет `filter` (цена от 300 ₽), `map` (название в верхнем регистре) и `doOnNext`. Например, салат «Цезарь» за 249.99 ₽ виден как полученный товар, но не проходит фильтр. Это демонстрация операторов Reactor, а не отдельная бизнес-операция frontend.
4. Fire-and-Forget: клиент отправляет изменение статуса доставки №1 на `ASSEMBLY` («В сборке»), сервер сохраняет статус и пишет об этом в журнал. Завершение `send()` означает отправку, а не подтверждение обработки сервером. Ошибка такого события доступна только в журнале сервера.
5. Channel: клиент отправляет четыре изменения количества в доставке №1 с интервалом 500 мс: пицца — 4 шт., несуществующий товар 999, салат — 0 шт., салат — 3 шт. Сервер сохраняет корректные изменения и возвращает результаты с задержкой 200 мс. Ответ на первый запрос появляется до завершения входного потока. Ошибки дают результаты `ERROR`, после которых обрабатывается следующий корректный запрос.
6. Повторное чтение доставки и её состава показывает сохранённый статус и количества. При повторном запуске клиента значения уже могут совпадать с отправляемыми; перезапуск сервера восстанавливает начальные данные.

Перед изменениями клиент получает состав доставки №1: пицца (2 шт.) и салат (1 шт.) — отдельными сообщениями, как данные для раскрываемой строки `GoodsList` во frontend.

Пример фрагмента вывода (время зависит от запуска):

```text
[12:00:00.400] Получен товар №1 — 599.99 ₽
[12:00:00.400] Reactor: ПИЦЦА "МАРГАРИТА" — 599.99 ₽
[12:00:00.800] Получен товар №2 — 249.99 ₽
[12:00:01.200] Получен товар №3 — 399.99 ₽
[12:00:01.600] Получен товар №4 — 199.99 ₽
```

Сервер не собирает поток в список перед отправкой. `delayElements` выдаёт элементы постепенно, клиент использует `limitRate(1)` для ограничения спроса. В Channel `concatMap` сохраняет порядок запросов. Вызов `block()` используется только на границе консольного приложения, чтобы процесс дождался завершения; серверные обработчики не блокируются.

Ошибка запроса карточки или неизвестного склада/доставки передаётся как RSocket ERROR. В Channel ошибки отдельных изменений передаются в структурированных результатах, чтобы один неверный элемент не завершал весь обмен. Нельзя менять количество отсутствующей позиции доставки; количество должно быть положительным. Ошибочное изменение не меняет состояние. Таймауты, ошибки транспорта и неожиданные ошибки завершают демонстрацию с диагностикой; автоматического повторения событий нет.

## Проверка

```powershell
mvn test
```

Интеграционные тесты поднимают сервер на свободном TCP-порту и проверяют карточки товара, склада и доставки, вложенные позиции `GoodsList`, ошибки отсутствующих объектов, фильтрацию по доставке, постепенную выдачу с управлением спросом, обработку Fire-and-Forget и двусторонний Channel с продолжением после некорректных элементов.
